# PocketContext Atlas

PocketContext Atlas (executable `pocketcontext-atlas`, formerly PocketContext): local knowledge base built as one Go binary on `pocketcontext-core`. Read README.md and docs/data-model.md before changes.

- Keep the project to the database file, `storage/`, `pocketcontext.json` and the binary. Everything machine-specific (working copy, logs, local key, unpacked assets, tokens) belongs in the per-machine cache. Never write PocketBase runtime files (`.notify`, `auxiliary.db`, `types.d.ts`, backups) into the project folder.
- Never let the server open the synced database directly. Copy it in on start and write back only through consistent snapshots and atomic renames. Never overwrite a synced file that changed elsewhere; keep both and require an explicit `recover`.
- The binary stores any file as an immutable source but extracts only UTF-8 text. Other formats (PDF, images, audio, office documents) are converted by the user's agent and recorded with `extract` as derived `agent-text` renditions. Never parse PDFs, images or audio in the binary. The core knowledge base must not depend on external tools or Python. Network services are limited to the explicit tunnel and HTTPS exceptions below.
  The private-tunnel exception is the opt-in `tunnel` command (`pocketcontext-core/tunnel`), which uses the tailcat library and its relays: it admits only the project's service, proxies it to its verified private socket or `127.0.0.1`, keeps its identity in the per-machine cache and avoids unsolicited address logging. Explicit invitation output shares the address and one-time code in the user's setup chat. Do not widen it (other ports, forwarding through the server, UDP, exit nodes, shells or files), and keep `build-tags.txt` in step with the tailcat release in `go.mod`.
- Keep authentication on: default private local socket or loopback, transport-aware Host check, own-origin CORS, ordinary `users` tokens. The opt-in `serve --headless --domain HOST` public HTTPS listener is the only public exception: exact configured Host/Origin, allowlisted reader/auth/knowledge routes, no dashboard or local management. The local key never leaves the private cache. Public connections never gain local privileges, including when their peer is loopback.
- PocketContext is single-user: one hidden account per project, and spaces are partitions, not an access boundary (see `docs/spaces.md`). SQL reads the live database directly and search indexes are shared. Do not reintroduce accounts, memberships, roles or per-requester filtering without a design.
- Remote mode (`--url`) is a client only: it never resolves or creates a database, never starts a server and never reads the local key. It accepts loopback URLs only and stores a token, never a password.
- PocketContext is a full fork. Review security fixes in its origin (see `docs/origin.md`) and in the vendored server (`internal/pocketcontext/VENDORED.md`, core's `VENDORED.md`) and port them by hand.
- Never reintroduce the retired product name outside `docs/origin.md`: not in files, file names, messages, tests or the binary. `tests/name_check.py` enforces it.
- Windows is a supported platform: use `filepath`, `sqliteuri.File` for SQLite URIs, and platform files for locks and process creation.
- Tests use synthetic notes in temporary folders. After changes run `go test ./...` (CGO, tags in `build-tags.txt`), `python3 tests/name_check.py --binary bin/pocketcontext-atlas` and `python3 tests/e2e.py --binary bin/pocketcontext-atlas`; rebuild `ui/dist` first when the reader changes.
- Never commit `bin/`, `ui/dist`, databases or real notes.

- 0.13.0 profiles and per-project skills live in the private user configuration directory, never the synced project. Preserve stable instance checks, legacy skills during router replacement, and explicit invitation handoffs. Since 0.14.0 the complete client prompt, invitation, one-time codes and reader sign-in links are authorized in the user's setup chats; do not require private file transfer or rotate addresses for this intended use. These still grant access: codes expire, but tunnel addresses retain connectivity until rotated. Passwords, tokens, local keys and private identity keys stay out of chat.

- Since 0.15.0, the CLI and running server must use the same release; keep status/stop usable for diagnosing mismatches. Database format 1 is inferred from the unchanged 0.11+ migration ledger. Check both application and PocketBase migrations before bootstrap; preserve snapshot write-back for system migrations. Installer replacement requires POCKETCONTEXT_REPLACE_VERSION matching the observed executable. Since 0.25.0 the shared server lives in `pocketcontext-core` (pinned by tag, no replace directive); the Atlas identity is `internal/atlaspolicy`. The public route allowlist is frozen by `internal/appconfig/testdata/public_routes.json`; change it only with a deliberate review. Names outside the Atlas identity table (cache root, database and config file, `POCKETCONTEXT_*`, `pocketcontext-container`, `/storage`, backup format) are a compatibility format. Follow docs/upgrades.md; never treat a binary replacement as a database migration or a running-process restart.

- Since 0.16.0, inspect the current session before reader setup: `environment` is offline; default `open` skips SSH, headless and uncertain sessions before starting a server, enabling TCP or issuing a reader code. `--no-browser` explicitly requests a link for a known reachable browser; `--skip-reader` omits it, including during CLI pairing. Agent/tool knowledge of remote execution overrides optimistic environment signals. SSH does not authorize a tunnel, but do not ask again when remote access is already requested. Never claim a launched helper proves the reader opened. See docs/reader-setup.md.

- Since 0.16.1, after the server-agent desktop handoff ask the user to return with confirmed reader access or the desktop error/completion report. Keep reader access pending until confirmed. The desktop client generates the fresh reader link after connection; the handoff must not contain a pre-generated reader URL. Follow docs/reader-setup.md for fallback without repeating authenticated pairing.

- Since 0.16.2, `tunnel serve` starts an initialized project headlessly when needed and reuses compatible running servers without changing listeners. Acquire the tunnel lock before startup and check readiness before loading or rotating tunnel identity. Tunnel exit leaves the server running; `stop` separately flushes and stops it.

- Since 0.17.0, `serve --headless --tunnel` owns server and tunnel in one foreground process. It requires an initialized stopped project, acquires the tunnel lock before startup, starts the tunnel only after socket readiness, and stops both through normal database write-back. Preserve independent `tunnel serve` behavior. Service managers own restart policy; do not add detached children or automatic database recovery.

- Since 0.18.0, native HTTPS is explicitly enabled with `serve --headless --domain HOST`, optionally alongside `--tunnel`. ACME contact, certificates and private keys are machine-local; no secrets or hosting configuration in the synced project. Let’s Encrypt is the explicit network-service exception for opt-in HTTPS issuance/renewal. Port 80 serves only ACME and HTTPS redirects; the application uses 443. Preserve local-only defaults and private management. `open --public` is a local command that issues a two-minute HTTPS sign-in link from the already-running service, even over SSH, without opening a browser or claiming external reachability. Follow docs/https.md; use external TLS verification and user-confirmed phone access. OS services own restart policy.

- Since 0.22.0, built-in reader chat and ACP host execution are removed. External agents use the authenticated CLI/API and installed skills. Leave historical machine-local chat files untouched; they are not knowledge records.

- Since 0.23.0, `serve --headless --domain HOST --mcp` explicitly enables remote MCP and OAuth on that domain. Preserve ordinary knowledge request hooks, audience-bound grants, PKCE, consent and revocation. OAuth state stays private and machine-local, outside the synced knowledge database. No MCP tool may expose local administration, shell execution, arbitrary host paths or network fetching. Reader sign-in links can bootstrap consent without revealing or resetting the project password.

- Hosted mode is an explicit deployment exception: one account, container, domain and persistent volume; ONCE terminates HTTPS and an isolated HTTP listener preserves the public route/Host/Origin boundary. Hosted users authenticate through PocketBase email OTP with runtime SMTP credentials; no public password login or private tunnel. Do not change existing local/native-HTTPS behavior or automatically convert a local project. Keep runtime credentials outside project settings and database persistence. The container supervisor owns complete private S3 backups (daily and before upgrades, 30-day retention), with one writer, explicit initialization and verified isolated restores. No Litestream. Automatic deployment is limited to explicitly enrolled PocketDeploy targets: validated main releases, a restricted repository key, sequential stop-first replacement and verified pre-upgrade backups. Unenrolled instances remain manually digest-pinned. See `docs/hosting.md`.

- Every push to `main` is a production deployment. The enrolled hosted instances (Ada, Alberto, Vamsi) follow `:latest` from `main`, not tagged releases, and hold other people's knowledge. Each successful image pipeline restarts all three (stop-first, brief outage, MCP sessions drop). So:
  - Keep `main` releasable; finish and test work before pushing, and batch small changes.
  - A change to the database format, an application or PocketBase migration, or anything that cannot be rolled back by redeploying the previous digest must not reach `main` while delivery runs. Set the repository variable `CONTEXT_DEPLOY_PAUSED=true` first, cut a release, upgrade the instances manually with verified backups, then unpause.
  - After pushing a change to sign-in, OTP email, OAuth or MCP, ask the owner to sign in on a hosted instance; `/up` health does not cover these flows.
  - Record each delivered source revision and digest; rollback uses that explicit digest and a compatible backup, never a historical `latest`.
